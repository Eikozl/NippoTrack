Foreign-key conversion
----------------------
All listed FKs retain `ON DELETE CASCADE`; PostgreSQL's default `ON UPDATE NO ACTION`
is semantically equivalent to the source's `ON UPDATE RESTRICT` because JLT primary
keys are immutable application identifiers.

* kanji_vocabulary.id_kanji -> kanji.id_kanji
* kanji_vocabulary.id_vocabulary -> vocabulary.id_vocabulary
* session_grammar.id_session -> study_sessions.id_session
* session_grammar.id_grammar -> grammar_points.id_grammar
* session_kanji.id_session -> study_sessions.id_session
* session_kanji.id_kanji -> kanji.id_kanji
* session_vocabulary.id_session -> study_sessions.id_session
* session_vocabulary.id_vocabulary -> vocabulary.id_vocabulary
* session_writings.id_session -> study_sessions.id_session (also UNIQUE)
* usage_examples.id_vocabulary -> vocabulary.id_vocabulary
* content_entry_sessions.id_content_entry -> content_entries.id_content_entry
* content_entry_sessions.id_session -> study_sessions.id_session
* each note_* table id_note -> notes.id_note; its second id -> the matching V1 entity
* each tag_* table id_tag -> tags.id_tag; its second id -> the matching V1 entity
* review_items.id_vocabulary -> vocabulary.id_vocabulary
* review_items.id_kanji -> kanji.id_kanji
* review_items.id_grammar -> grammar_points.id_grammar
* review_events.id_review_item -> review_items.id_review_item

Indexes and constraints
-----------------------
Preserved indexes are created for all source lookup paths:
* V1: vocabulary (word, jlpt_level, status); kanji and grammar_points (jlpt_level,
  status); study_sessions (session_date, category); all V1 junction reverse FKs.
* V2: usage_examples (id_vocabulary, id_usage_example); goals (is_active, due_date)
  and (goal_type, period_type); content_entries date paths; every relationship's
  reverse FK; notes (category, updated_at); review_items (due_on); review_events
  (id_review_item, reviewed_at).
* Source uniqueness is preserved: `kanji.character_kanji`, `grammar_points.grammar_point`,
  `tags.normalized_name`, one `session_writings` row per session, and one review item
  per vocabulary/kanji/grammar entity.
* Value constraints are preserved for JLPT level, learning status, V1 session category
  allowlist, positive duration/target, goal type/period/date relationship, content
  type/ranges, notes category, non-negative review intervals, and exactly one review
  target. The review target check is PostgreSQL-native boolean-to-integer arithmetic.

Identity definitions
--------------------
Every former `INT AUTO_INCREMENT` key is `integer GENERATED BY DEFAULT AS IDENTITY`.
`BY DEFAULT` intentionally permits Phase D's controlled import to insert the existing
MariaDB IDs so all FK relationships and URLs remain stable. After the import, its
sequence will be advanced with `setval` to the imported maximum. No data or sequence
has been imported/advanced in this phase.

updated_at strategy
-------------------
`jlt_set_updated_at()` is a PostgreSQL trigger function. A BEFORE UPDATE trigger uses
it on vocabulary, kanji, grammar_points, study_sessions, session_writings,
usage_examples, goals, content_entries, notes, tags, and review_items. It supplies
the MariaDB `ON UPDATE CURRENT_TIMESTAMP` behavior centrally and does not require
individual application queries to remember `updated_at`.

Timestamps use `timestamptz`; date-only domain values remain `date`. Application
cutover must set a consistent connection/session timezone (the JLT operating timezone
is America/Santo_Domingo) before porting queries that rely on `CURRENT_DATE`.

Migration runner behavior
-------------------------
`npm run postgres:migrate`:
1. Loads only `.env.postgres` (or a deliberately supplied `POSTGRES_ENV_FILE`), never
   the active MariaDB `.env` by default.
2. Reads only filenames matching `NNN_lowercase_name.sql` from
   `server/db/migrations-postgres/`, in lexical order.
3. Starts one transaction and obtains a transaction-scoped advisory lock to prevent
   concurrent runners.
4. Creates `schema_migrations(filename, checksum, applied_at)` if absent.
5. Applies only unseen files, stores SHA-256 checksum, and commits all work together.
6. Refuses to continue if an already recorded migration was edited. On failure it
   rolls back that complete run.

`npm run postgres:check` reports the connected PostgreSQL database, user, server
version, timezone, and public-table count. Neither command touches MariaDB.

Semantic differences from MariaDB
---------------------------------
* PostgreSQL uses `$1, $2, ...` parameter placeholders and `RETURNING`; the current
  `mysql2` query layer and `?` placeholders remain active until a later cutover phase.
  This phase deliberately does not alter runtime database behavior.
* `TINYINT(1)` `goals.is_active` becomes a real boolean (`true`/`false`). API mapping
  will normalize it later; database meaning is unchanged.
* MariaDB `TIMESTAMP`/`DATETIME` maps to `timestamptz` for event/audit timestamps;
  timezone conversion must be explicit in the later import and query port.
* PostgreSQL has no `ON UPDATE CURRENT_TIMESTAMP` column clause; equivalent behavior
  is implemented by the shared trigger.
* MySQL index prefix/collation and case/accent behavior are not copied implicitly.
  The baseline uses PostgreSQL defaults; any search-equivalence decision is reserved
  for the SQL/query compatibility phase, before cutover.
* The source has explicit `ON UPDATE RESTRICT`. PostgreSQL omits it because its default
  `NO ACTION` protects referenced keys equivalently for JLT's non-deferrable usage.
* `INTEGER` and `SMALLINT` replace display-width MySQL INT/TINYINT. Checks preserve
  valid JLT ranges; PostgreSQL rejects numeric values outside their native ranges.
