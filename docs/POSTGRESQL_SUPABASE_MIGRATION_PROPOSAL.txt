JAPANESE LEARNING TRACKER
POSTGRESQL + SUPABASE MIGRATION PROPOSAL

Status: proposal only. No application files, database schema, data, migrations,
or Supabase settings have been changed by this proposal.

SOURCE DOCUMENT AND SCOPE
========================================================================

The attached master guide requires an incremental MariaDB/MySQL -> PostgreSQL
-> Supabase migration. It explicitly requires a compatibility audit before any
implementation work.

This proposal preserves the existing JLT V1, V1.1, and V2 behavior. It does
not propose a rewrite, an ORM, client-side database access, or a redesign of
the approved relational model.

KNOWN COMPATIBILITY WORK
========================================================================

The PostgreSQL migration must convert these MySQL/MariaDB behaviors:

  1. mysql2/promise -> pg.
  2. Query placeholders: ? -> $1, $2, $3, ...
  3. AUTO_INCREMENT -> GENERATED BY DEFAULT AS IDENTITY.
  4. UNSIGNED types -> signed types plus CHECK constraints where needed.
  5. TINYINT(1) -> BOOLEAN where appropriate.
  6. CURDATE, NOW, DATE_ADD, DATE_SUB, WEEKDAY, YEARWEEK, DATE_FORMAT, and
     MySQL date interval syntax -> deliberate PostgreSQL equivalents.
  7. ON DUPLICATE KEY UPDATE -> ON CONFLICT (...) DO UPDATE.
  8. SELECT DATABASE() -> SELECT current_database().
  9. MySQL ER_* errors -> PostgreSQL SQLSTATE errors, such as 23505, 23503,
     23514, and 23502.
 10. MySQL engine, charset, and collation clauses -> PostgreSQL-native DDL.
 11. SHOW TABLES / SHOW CREATE TABLE backup behavior -> PostgreSQL-native
     backup tooling.

The highest-risk items are romaji-aware SQL search, dynamic placeholders,
calendar/timezone calculations, transactions, identity sequences after data
import, and backup/migration tooling.

PROPOSED EXECUTION PLAN
========================================================================

PHASE A - COMPATIBILITY AUDIT (FIRST; NO WRITES)

Deliver a written compatibility report containing:
  - Every database call and transaction boundary.
  - Every MySQL-specific query and schema construct.
  - Every affected migration, script, helper, controller, and test.
  - Current schema summary and database integrity baseline.
  - A PostgreSQL conversion map for each identified pattern.
  - Risks, rollback points, and focused test coverage.

No source files, database rows, migrations, or Supabase resources will be
changed in Phase A.

PHASE B - POSTGRESQL SCHEMA AND MIGRATION HISTORY

Create PostgreSQL-specific, version-controlled migrations in a separate path:

  server/db/migrations-postgres/

Keep the historical MySQL migrations intact. Create a PostgreSQL baseline that
preserves table names, columns, primary/foreign keys, cascade behavior,
constraints, indexes, Japanese text fields, and V2 relationships.

Add a schema_migrations table and a PostgreSQL migration runner that applies
pending versions exactly once and records a version only after success.

PHASE C - NODE/EXPRESS DATABASE LAYER

Replace the active mysql2 runtime dependency with pg while retaining Express as
the sole database boundary.

The target server configuration is:

  DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
  NODE_ENV=development
  PORT=3000

Database credentials remain server-side. No DATABASE_URL or database secret is
added to the Vite client or any VITE_* variable.

PHASE D - INCREMENTAL SQL CONVERSION

Convert and test one area at a time, in this order:

  1. Health and database configuration.
  2. Vocabulary.
  3. Kanji.
  4. Grammar.
  5. Study sessions and structured writing.
  6. Dashboard, statistics, streaks, and calendar.
  7. Goals.
  8. Content, notes, and tags with their links.
  9. Review queue and events.
 10. Export, backups, and migration tooling.

Every dynamic query will use a parameter-binding helper that produces numbered
PostgreSQL placeholders. Raw user input will remain parameterized.

PHASE E - LOCAL DATA MIGRATION AND VALIDATION

Before importing data:
  - Stop writes.
  - Create and verify a MariaDB logical backup.
  - Capture row counts and maximum primary keys per table.
  - Check foreign-key orphans and duplicates.
  - Preserve representative Japanese text samples.

After importing into local PostgreSQL:
  - Compare row counts for every V1 and V2 table.
  - Check all PK/FK relationships, indexes, unique constraints, and checks.
  - Reset identity sequences above each imported maximum ID.
  - Verify Japanese text round-trips exactly.
  - Verify new inserts do not collide with imported IDs.

PHASE F - LOCAL POSTGRESQL ACCEPTANCE

Run JLT locally against PostgreSQL and verify:
  - API health, CRUD, session links, writing, examples, goals, content,
    notes, tags, review, quick add, streaks, calendar, and exports.
  - Romaji and Japanese search behavior.
  - Transactions and rollbacks.
  - Existing unit tests plus new real PostgreSQL integration tests.

Only after this phase is fully green will Supabase be considered.

PHASE G/H/I - SUPABASE

  1. Create/configure a Supabase development project.
  2. Store the connection string only in server-side secrets.
  3. Use version-controlled PostgreSQL migrations, not manual dashboard edits.
  4. Migrate the validated PostgreSQL schema and data.
  5. Verify counts, constraints, sequences, Japanese text, and latency.
  6. Run the local Express application against Supabase.

PHASE J - VERCEL READINESS

Only after Supabase-backed local acceptance:
  - Choose a Supabase runtime connection mode appropriate for serverless use.
  - Configure server-side DATABASE_URL in Vercel.
  - Keep migrations outside HTTP request handling.
  - Document separate development and production databases.

TEST PLAN
========================================================================

Keep the current test suite as a behavioral baseline and add PostgreSQL
integration coverage for:
  - Database health and selected database name.
  - CRUD and safe error mapping.
  - Unique, foreign-key, not-null, and CHECK constraints.
  - Cascading deletes and transactions/rollbacks.
  - Search, romaji ranking, pagination, and Japanese text.
  - Goals, review due dates, streaks, and timezone boundaries.
  - PostgreSQL migrations, backup/restore, and imported identity sequences.

ROLLBACK PLAN
========================================================================

  - Do not alter or discard MariaDB while PostgreSQL is being validated.
  - Create a verified backup before every data or destructive schema step.
  - Keep MySQL migrations as project history and PostgreSQL migrations in a
    separate location.
  - Use configuration to choose the active database engine during transition.
  - Do not connect to Supabase production before local PostgreSQL acceptance.
  - Do not delete the original MariaDB backup until PostgreSQL and Supabase
    acceptance are complete.

APPROVAL REQUEST
========================================================================

If approved, the next action is PHASE A ONLY: a read-only compatibility audit
and written report. No code, migration, database, or Supabase changes will be
made until that audit is delivered and approved.
