JLT MULTI-USER AUTHENTICATION & DATA ISOLATION MASTER IMPLEMENTATION GUIDE
=======================================================================

PROJECT
Japanese Learning Tracker (JLT)

CURRENT STATUS
--------------
JLT V3 is functionally complete.

Completed production-hardening work that MUST be preserved:
- Express remains the only application/database boundary.
- PostgreSQL/Supabase is the active database platform.
- jlt_runtime exists as a dedicated least-privilege runtime role.
- jlt_runtime is not a superuser and cannot manage roles/databases, replicate, bypass RLS, own JLT objects, or access schema_migrations.
- All 25 application tables have RLS enabled and forced.
- Each application table has one explicit CRUD policy scoped to jlt_runtime.
- anon, authenticated, and PUBLIC have no application-data privileges.
- Default privileges have been hardened so future migrations do not reintroduce public grants.
- Runtime fails closed if jlt_runtime credentials are missing.
- Admin/migration credentials remain separate from runtime credentials.
- Runtime credential rotation is idempotent.
- Database security verification is automated.
- Supabase DEV has been verified with the hardened role.
- Current regression suite passes against Supabase using jlt_runtime.
- Production frontend build passes.
- Rate limiting has already been introduced.
- No Vercel deployment has started.

IMPORTANT ROADMAP CHANGE
------------------------
Pause the remaining Vercel/deployment work.

The architecture is changing from:
    single-user protected application
to:
    simple multi-user application with strict per-user data isolation

This is NOT a SaaS conversion.

Do NOT add:
- organizations
- teams
- billing
- subscriptions
- plans
- tenant administration
- public profiles
- invitations
- OAuth providers unless explicitly requested later
- role-management infrastructure unless technically required
- social features
- admin dashboards
- browser-direct PostgreSQL access

The goal is only to add:
- registration
- email/password authentication
- email verification
- sign in
- sign out
- session persistence
- forgot-password flow
- password reset
- strict per-user ownership and isolation of JLT data

AUTHENTICATION STRATEGY
-----------------------
Use Supabase Auth for identity and authentication.

Do NOT build password hashing, verification-token generation, recovery-token generation,
refresh-token rotation, or password storage manually.

Use Supabase Auth because it already provides:
- user identity
- password hashing
- session lifecycle
- access/refresh token handling
- email verification
- password recovery
- account confirmation state

For production email delivery:
- DO NOT rely on Supabase's built-in test SMTP service.
- Plan for a custom external SMTP provider.
- Keep SMTP configuration outside Git.
- Keep DEV and future PROD email/redirect configuration separate.

TARGET ARCHITECTURE
-------------------
Browser

  | Supabase Auth session / access token

  | Derive req.user.id server-side

The browser may use Supabase Auth client capabilities required for authentication,

PHASE 1 — OWNERSHIP ARCHITECTURE AUDIT
=======================================================================

DO NOT modify the schema immediately.

First audit all 25 application tables and classify each table into one of these categories:

A. USER-OWNED ROOT ENTITY
   A table representing data directly owned by one user.
   Likely examples:
   - study_sessions
   - vocabulary
   - kanji
   - grammar_points
   - goals
   - content_entries
   - notes
   - tags
   - review_items

B. USER-OWNED CHILD ENTITY
   A table whose ownership may be derived from a user-owned parent.
   Example:
   - review_events through review_items
   - usage_examples through vocabulary or kanji if that matches actual schema semantics
   - session_writings through study_sessions

C. JUNCTION / RELATIONSHIP TABLE
   Ownership may be derived through both referenced parent entities.
   Examples:
   - session_vocabulary
   - session_kanji
   - session_grammar
   - kanji_vocabulary
   - note_study_sessions
   - note_vocabulary
   - note_kanji
   - note_grammar
   - tag_study_sessions
   - tag_vocabulary
   - tag_kanji
   - tag_grammar
   - content_entry_sessions

D. GLOBAL / SYSTEM ENTITY
   Only if the existing schema truly contains data intended to be shared globally.

For every table, document:
- table name
- classification
- direct user_id required? yes/no
- ownership derivation path
- relevant foreign keys
- relevant unique constraints
- relevant indexes
- current query files touching it
- current export/search/dashboard/statistics/review dependencies

DO NOT add user_id blindly to all 25 tables.

DELIVERABLE:
Produce an ownership map before implementation.

=======================================================================
PHASE 2 — UNIQUE CONSTRAINT & INDEX AUDIT
=======================================================================

Audit every UNIQUE constraint.

Any value that was globally unique in single-user mode may need to become user-scoped.

Example:
    UNIQUE(word)
may need to become:
    UNIQUE(user_id, word)

Possible examples to inspect:
- vocabulary term
- kanji character
- grammar identifier/name
- tag name
- user-created content identifiers

Do NOT assume every UNIQUE must change.

For each UNIQUE:
- document current behavior
- determine whether uniqueness should be global or per user
- propose exact replacement constraint if needed

Add indexes for ownership paths where query patterns require them.

At minimum, root-owned tables should generally have efficient user_id filtering.

Do not create redundant indexes where a composite unique/index already covers the access pattern.

=======================================================================
PHASE 3 — SUPABASE AUTH INTEGRATION DESIGN
=======================================================================

Replace the existing transitional single-password login system with Supabase Auth.

Required authentication features:

1. SIGN UP
   - email
   - password
   - confirm password in UI
   - request email confirmation

2. EMAIL VERIFICATION
   - unverified users must not receive full application access
   - handle verification redirect safely
   - show meaningful success/failure states

3. SIGN IN
   - email/password
   - establish Supabase session
   - restore session after page reload

4. SIGN OUT
   - invalidate session
   - return to auth screen
   - clear application state where needed

5. FORGOT PASSWORD
   - user submits email
   - use Supabase Auth recovery flow
   - return a non-enumerating response

6. RESET PASSWORD
   - handle recovery link
   - allow user to set a new password
   - handle invalid/expired recovery sessions safely

7. SESSION RESTORATION
   - application should restore authenticated state on reload
   - expired session should cleanly return to login

SECURITY REQUIREMENTS:
- Do not store application passwords.
- Do not hash passwords manually.
- Do not put auth secrets into client code.
- Do not expose service-role keys.
- Do not trust localStorage as proof of identity.
- Do not trust a user_id submitted by the browser.

=======================================================================
PHASE 4 — EXPRESS AUTHENTICATION BOUNDARY
=======================================================================

Every private API request must identify the authenticated Supabase user.

Express must verify the authenticated identity and expose an internal identity such as:

    req.user.id

The canonical user ID must come from the verified Supabase session/token.

NEVER derive authorization from:
- req.body.user_id
- req.query.user_id
- req.params.user_id
- client-side hidden fields
- localStorage user IDs

Private routes must fail with 401 when no valid identity exists.

Authorization failures must not reveal another user's resource existence.

Recommended behavior:
- unauthenticated -> 401
- authenticated but requesting another user's resource -> 404 or equivalent safe behavior

Keep health/public auth endpoints intentionally public only where required.

Rate limiting must remain active and should be reviewed for:
- sign in
- sign up
- password recovery
- general API access

Auth-specific limits may be stricter than the generic API limit.

=======================================================================
PHASE 5 — CREATE THE OWNER ACCOUNT BEFORE DATA MIGRATION
=======================================================================

The existing JLT dataset belongs to the project owner.

Before backfilling ownership:

1. Create the owner's real Supabase Auth account.
2. Confirm the email.
3. Obtain the resulting auth.users UUID.
4. Record that UUID only in the migration execution environment.
5. Do NOT hardcode the UUID permanently into application source code.

IMPORTANT:
The owner does NOT require a special "admin" role merely to own existing data.

Ownership is represented by:
    user_id = owner's auth.users.id

Do NOT add admin-role infrastructure unless a concrete product requirement appears later.

=======================================================================
PHASE 6 — STAGED DATABASE OWNERSHIP MIGRATION
=======================================================================

Use a safe staged migration.

DO NOT:
- recreate the database
- delete existing study data
- reset production-like data
- disable constraints broadly
- bypass verification

STAGE 1 — Add ownership columns
For each root-owned table requiring direct ownership:

    user_id UUID NULL

Add the column nullable first.

Reference Supabase auth.users only if the architecture and permissions allow this cleanly.
If using a direct FK to auth.users, verify migration/runtime implications carefully.

STAGE 2 — Backfill existing data
Set all existing root-owned rows to the owner's Supabase Auth UUID.

STAGE 3 — Validate ownership
Verify:
- zero root rows with NULL user_id
- zero broken parent/child ownership paths
- zero junction relationships crossing users
- all legacy rows resolve to the owner

STAGE 4 — Add required constraints/indexes
Add:
- user_id indexes
- composite UNIQUE constraints where required
- ownership-related FK constraints if appropriate

STAGE 5 — Enforce NOT NULL
Only after verification:
    ALTER COLUMN user_id SET NOT NULL

STAGE 6 — Re-run verification
Confirm:
- row counts unchanged
- relationships unchanged
- data content unchanged
- owner can access all migrated data
- no new orphan rows
- no cross-user relationships

PHASE 7 — QUERY ISOLATION
=======================================================================

Audit every SQL query that touches user-owned data.

This includes:
- SELECT
- INSERT
- UPDATE
- DELETE
- UPSERT
- search
- dashboard
- statistics
- streak
- review
- export
- calendar/history
- notes
- goals
- tags
- content
- usage examples
- relationship writes

Every root-level operation must be scoped to the authenticated user.

Example before:
    SELECT * FROM vocabulary WHERE id = $1;

Example after:
    SELECT * FROM vocabulary
    WHERE id = $1
      AND user_id = $2;

Example insert:
The browser must NOT send user_id as trusted ownership input.

Instead:
    INSERT INTO vocabulary (..., user_id)
    VALUES (..., req.user.id)

The authenticated user ID must be passed server-side.

AUDIT ALL QUERY-BUILDING HELPERS.
Do not fix only obvious route handlers while leaving shared query helpers globally scoped.

=======================================================================
PHASE 8 — RELATIONSHIP / JUNCTION TABLE ISOLATION
=======================================================================

This phase is critical.

A user must never be able to create a relationship between:
- their own entity
and
- another user's entity

Example:
User A must not be able to link:
    A's study_session
to:
    B's vocabulary

Before inserting a relationship:
- validate ownership of all referenced parents
- preferably do so inside the same transaction where consistency matters

For junction tables without direct user_id:
ownership must be proven through their parent foreign keys.

Audit:
- kanji_vocabulary
- session_vocabulary
- session_kanji
- session_grammar
- content_entry_sessions
- note_* links
- tag_* links
- any other relationship table

Cross-user links must be impossible both:
- through normal API calls
- through manipulated IDs

=======================================================================
PHASE 9 — RLS STRATEGY AFTER MULTI-USER CONVERSION
=======================================================================

DO NOT weaken the current hardened database model.

Preserve:
- jlt_runtime as runtime role
- forced RLS
- no PUBLIC grants
- no anon/authenticated table grants
- no browser-direct application data access
- admin/runtime separation
- fail-closed credentials

IMPORTANT ARCHITECTURAL FACT:
Because Express connects as jlt_runtime, PostgreSQL sees jlt_runtime rather than the end user's Supabase role.

Therefore:
- per-user authorization remains an Express responsibility
- SQL queries must be scoped by req.user.id
- current jlt_runtime RLS remains a runtime-role boundary
- do not pretend current RLS alone provides per-user tenant isolation

Document this explicitly.

OPTIONAL DEFENSE-IN-DEPTH:
If a safe server-side session-context approach is considered later, evaluate it separately.
Do not introduce unnecessary PostgreSQL session/JWT complexity during this phase unless justified.
