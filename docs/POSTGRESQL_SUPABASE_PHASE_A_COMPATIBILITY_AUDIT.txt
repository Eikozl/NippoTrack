JAPANESE LEARNING TRACKER (JLT)
PHASE A - MYSQL/MARIADB TO POSTGRESQL COMPATIBILITY AUDIT

Audit status: COMPLETE
Date: 2026-08-30
Scope: read-only repository inspection and read-only MariaDB validation.

IMPORTANT ARCHITECTURAL DECISION
========================================================================

JLT will NOT become a permanent dual-engine MariaDB/MySQL + PostgreSQL
application.

MariaDB remains available only as a migration source, validation reference,
backup source, and rollback point during the transition. The completed
application runtime will use PostgreSQL as its single canonical database
engine. Supabase is a later PostgreSQL hosting target, not a second runtime
data-access architecture.

No application code, schema, MariaDB data, PostgreSQL data, migration file,
or Supabase configuration was changed during this audit.

Schema preservation requirements:

    CHECK rules, and ON DELETE CASCADE behavior.
  - Preserve V1/V2 model behavior; PostgreSQL conversion is not authorization
    to redesign entities or relationships.

  - goals.is_active is TINYINT(1); PostgreSQL should use BOOLEAN.

    their existing range CHECK constraints.
  - MySQL timestamp ON UPDATE behavior needs PostgreSQL triggers or explicit
    application-side updates. This is a manual-review schema item.

Current API shape assumptions coupled to mysql2:
  - pool.execute(...) resolves [rows, metadata].
  - pool.query(...) resolves [rows, metadata].
  - INSERT results use result.insertId and result.affectedRows.
  - Transactions use pool.getConnection(), beginTransaction(), commit(),
    rollback(), and release().

PostgreSQL target shape:
  - pool.query(sql, values) returns { rows, rowCount }.
  - INSERT paths must use RETURNING <primary_key> rather than insertId.
  - A transaction client comes from pool.connect(), uses BEGIN/COMMIT/ROLLBACK,
    and must be released in finally.
  - Implement a small database adapter/helper only if it removes mechanical
    driver-result differences without hiding SQL behavior. Do not add an ORM.

5. QUERY AND SQL COMPATIBILITY MAP
========================================================================

PLACEHOLDERS - REQUIRES CONVERSION
  Current: ?
  Target:  $1, $2, $3, ...
  Affected: all controllers, helpers, listHelpers, scripts, and sqlSearch.
  Requirement: create a safe numbered-parameter helper for dynamic SQL.

PAGINATION - PORTABLE AFTER PLACEHOLDER CONVERSION
  Current: LIMIT ? OFFSET ?
  Target:  LIMIT $n OFFSET $n+1
  Affected: listHelpers and paginated V1/V2 endpoints.

SEARCH / ROMAJI - MANUAL REVIEW
  Files:
    server/src/search/sqlSearch.js
    server/src/search/japaneseSearch.js
    server/src/search/optionRanking.js
    vocabularyController.js
    kanjiController.js
    grammarController.js
  Current SQL uses COALESCE, REPLACE, LIKE, CASE ordering, CONCAT, and dynamic
  comparison fragments with ? placeholders.
  PostgreSQL supports COALESCE, REPLACE, CASE, and CONCAT, but LIKE casing and
  collation semantics differ. Preserve the current matching/ranking contract
  with focused Japanese and romaji regression tests; choose LIKE/ILIKE or an
  explicit normalization strategy only after those tests pass.

DATE/TIME - MANUAL REVIEW / HIGH RISK
  Current MySQL patterns:
    CURDATE()
    NOW()
    DATE_ADD(CURDATE(), INTERVAL ? DAY)
    DATE_SUB(CURDATE(), INTERVAL N DAY)
    WEEKDAY(CURDATE())
    YEARWEEK(session_date, 1)
    DATE_FORMAT(...)
  Affected files:
    dashboardController.js
    reviewController.js
    v2Controller.js
  PostgreSQL candidates:
    CURRENT_DATE
    CURRENT_TIMESTAMP
    CURRENT_DATE + ($n * INTERVAL '1 day')
    CURRENT_DATE - INTERVAL 'N days'
    EXTRACT(ISODOW FROM CURRENT_DATE)
    date_trunc('week', CURRENT_DATE)
    to_char(...)
  Requirement: preserve the local calendar behavior for America/Santo_Domingo;
  do not assume UTC server time is the user calendar. Test Monday boundaries,
  dashboards, streaks, goals, and review due dates.

UPSERT - REQUIRES CONVERSION
  Current:
    sessionsController.js: ON DUPLICATE KEY UPDATE for session_writings.
    reviewController.js: ON DUPLICATE KEY UPDATE for review_items.
  Target:
    ON CONFLICT (<unique column>) DO UPDATE SET ...
  Requirement: name the exact unique conflict targets and preserve no-op or
  update semantics.

HEALTH CHECK - REQUIRES CONVERSION
  Current: SELECT DATABASE() AS database_name
  Files: healthController.js, check-db.js, backup-db.js, run-migration.js.
  Target: SELECT current_database() AS database_name.

MYSQL ADMIN/INTROSPECTION - REQUIRES REPLACEMENT
  Current:
    SHOW TABLES
    SHOW CREATE TABLE
    backtick-delimited identifiers
  Files: backup-db.js and check-db.js.
  Target: pg_dump/pg_restore for canonical PostgreSQL backups, and
  information_schema/pg_catalog only where an application diagnostic needs it.
  Do not treat JSON schema dumps as a replacement for a verified pg_dump.

ERROR MAPPING - REQUIRES CONVERSION
  File: server/src/errors/http.js
  Current MySQL codes:
    ER_DUP_ENTRY
    ER_NO_REFERENCED_ROW_2
    ER_ROW_IS_REFERENCED_2
  PostgreSQL SQLSTATE mapping:
    23505 -> unique violation / HTTP 409
    23503 -> foreign-key violation / safe related-record error
    23514 -> CHECK violation / HTTP 400
    23502 -> not-null violation / HTTP 400
  Requirement: preserve safe public messages and keep raw DB errors server-side.

Current MySQL transaction API:
  getConnection -> beginTransaction -> execute -> commit/rollback -> release

PostgreSQL conversion requirement:
  pool.connect -> BEGIN -> client.query -> COMMIT/ROLLBACK -> client.release

High-priority transaction integration tests:
  - Session create/update with all V1 relationships and writing.
  - Vocabulary/example atomic creation.
  - Content, note, and tag link replacement.
  - Review event insertion plus due-date update.
  - Rollback when one relationship insert fails.

9. RISK REGISTER
========================================================================

HIGH
  1. Timezone behavior: current MySQL date functions use database server time;
     PostgreSQL must preserve America/Santo_Domingo calendar semantics.
  2. Search behavior: LIKE/collation differences can alter romaji/Japanese
     matching and ranking.
  3. Dynamic SQL placeholders: $n numbering must remain aligned with every
     dynamic clause and ordering parameter.
  4. Import sequences: explicit IDs require PostgreSQL identity sequences to
     be advanced beyond current maximum IDs.
  5. updated_at behavior: MySQL ON UPDATE timestamps require an explicit
     PostgreSQL equivalent.

MEDIUM
  6. mysql2 result-shape assumptions are spread across controllers/tests.
  7. Review upserts and session-writing upserts need exact ON CONFLICT targets.
  8. Backup tooling changes from MySQL introspection to PostgreSQL-native tools.
  9. Vercel/Supabase pooling must be decided only after local PostgreSQL works.

LOW
 10. Japanese UTF-8 storage itself is well supported by PostgreSQL; the risk is
     validation and import encoding, not lack of Unicode support.

11. IMPLEMENTATION ORDER AFTER APPROVAL
========================================================================

  1. Establish a local PostgreSQL target and a verified MariaDB backup point.
  2. Create PostgreSQL schema baseline/migration tracking only.
  3. Migrate the database adapter/driver and health endpoint.
  4. Convert SQL incrementally, with focused tests after each controller group.
  5. Migrate and validate data into local PostgreSQL.
  6. Run the entire application locally against PostgreSQL.
  7. Replace PostgreSQL backup/migration tooling and run real integration tests.
  8. Only then configure Supabase development.
  9. Only after Supabase-backed local acceptance, prepare Vercel.

12. ROLLBACK PLAN
========================================================================

  - MariaDB remains unchanged during Phase A and as a rollback source during
    the entire local PostgreSQL transition.
  - Create a verified MariaDB backup before any later data operation.
  - Do not delete or overwrite the migration-source database.
  - Make PostgreSQL schema/data changes only against a separate local target
    until local acceptance is complete.
  - Keep engine selection transitional only; the production/runtime end state
    is PostgreSQL alone, not permanent dual-engine support.
  - Do not create, migrate, or use Supabase production until local PostgreSQL
    acceptance and data validation are complete.

PHASE A CONCLUSION
========================================================================

The repository is a suitable candidate for an incremental PostgreSQL migration,
but no blind SQL replacement is safe. The PostgreSQL conversion must explicitly
address driver result shapes, placeholders, migrations, date/time behavior,
romaji search semantics, transactions, error codes, identity sequences, and
backup tooling.

Recommended next approval:
  Approve Phase B/C preparation for a separate local PostgreSQL target and
  PostgreSQL-native migration baseline. Do not connect to Supabase yet.
